# CU Ways: one-to-one visual migration recovery plan

**Status:** Implementation specification following the human rejection of React migration fidelity on 1 November 2026. This document plans the correction; it does not claim that the correction has been implemented or accepted.

**Working repository:** `Champy2005/cu-ways-ux-ui`, private. The existing frontend and backend remain independent and unchanged. The original local `UX UI` implementation and selected comparison inputs must remain available throughout recovery.

**Scope:** US025, US026, US027, US028 and US034; all 94 existing scenario identities, their meaningful state transitions, and their shared product components. The migration must preserve the original responsive design rather than replace it with a plausible alternative.

**Current verdict:** The workbench architecture is usable. Its visual implementation is rejected. Passing React interaction, geometry and internal-consistency checks does not reverse that verdict. No current React capture should become an accepted migration reference merely because the capture process is reproducible.

**Operational purpose:** Give the implementing agent an executable sequence for recovering fidelity, with clear source ownership, measurements, responsive contracts, stop conditions and evidence. Routine work should still begin with the short repository instructions and a focused context query. This long document is the recovery specification, not a new historical design book.

## 1. The correction objective

The objective is to make the React implementation reproduce the intended original interface at equivalent states and environments. React is the implementation vehicle. It is not permission to change page composition, replace navigation with story shortcuts, redistribute metadata, invent generic cards, or choose new control dimensions. A successful migration should be difficult to distinguish from the source when both are displayed at the same product viewport, with the same data, theme, material, text setting and interaction state.

One-to-one fidelity does not mean copying a few screenshot coordinates into fixed CSS. It means preserving the rules that generated those coordinates. The result must continue to respond correctly between sampled widths. It must preserve the source's caps, gutters, container conditions, viewport scaling, text enlargement, stacking order, floating action tray and compact navigation behavior. If a component is content-sized in one context and panel-sized in another, that distinction must survive the move.

The immediate human observations identify a structural problem, not six unrelated cosmetic requests. The desktop navigation has incorrect destinations and labels. Navigation sizing and selected treatment differ between themes. Start job and Refresh job use incompatible width policies. The page's information hierarchy, content origin and column proportions shifted. Those changes share an underlying cause: the migration reconstructed the interface using generalized React compositions instead of first preserving the original visual contract.

Recovery therefore begins with the original rendered result and complete source cascade. The implementer must establish what the original actually does before deciding where a React component belongs. A component API should express a verified source distinction. It should not force source pages into whichever arrangement is convenient for the new API. When the original has a Contract panel and a Surveys panel, a generic Job summary plus Job overview is not an equivalent representation merely because the same underlying facts remain visible.

The product header must use the explicitly required desktop destinations: **Overview, Services, My Jobs, Invitations and Profile**. Story selection remains in Storybook's manager and tooling. Product navigation must not become My Jobs, Proof, Completion, Cancellation and Reviews. That replacement changes the product model and makes visual review harder because the workbench UI and product UI become entangled.

The target is strict fidelity with an explicit, small list of authorized differences. Accessibility repairs, nonblocking operation recovery and later human corrections can justify differences where the original has a demonstrated defect. They do not justify silent redesign. Every intentional difference needs a scope, reason, owner and verification method. An agent's personal preference for a cleaner arrangement is not sufficient authorization.

Completion means both the behavioral migration and the visual migration have evidence. All 94 cases must remain reachable and meaningful. The original-to-React comparison must cover the relevant component, its composition and its page. The user should receive a focused review of real changes and unresolved choices, not another declaration that hundreds of internally coherent React screenshots look acceptable.

## 2. Why the previous verification missed the problem

The earlier work invested heavily in canonical components, typed states, architecture rules and automated captures. Those are useful foundations. They answered questions such as whether the same Accepted badge used the same React styling across pages, whether a modal could be dismissed, whether loading had a recovery path, and whether a local change repainted a protected sibling. They did not establish whether the canonical React badge, modal, card or shell matched the source design.

This distinction is the central failure mode. Internal consistency can make a wrong design uniformly wrong. A page can have no overflow, no duplicate dispatch, no inaccessible label and no inconsistent semantic token while still using the wrong width, wrong hierarchy, wrong navigation labels and wrong breakpoint. Those properties need independent fidelity checks against the original. They cannot be inferred from reuse of one component implementation.

The first full capture runs had no durable visual reference. Their visual comparison result was inconclusive. A missing-reference result should have prevented any implication of original parity. Capturing the new implementation and then treating those captures as the provisional migration truth would only preserve the drift. Provisional references can be useful during development, but their origin and purpose must remain explicit. A provisional React snapshot is not evidence that the React snapshot resembles the original.

Broad contact sheets were effective at detecting obvious clipping, duplicated error groups, unusable enlarged dialogs and missing control boundaries. They were weak at comparing subtle typography, source spacing, navigation selection, contextual action width or card ordering. A desktop page reduced to a small thumbnail can look balanced even when its content width differs by hundreds of pixels. A large blank canvas further hides proportional errors. The next workflow must use same-scale paired crops and measured anchors before broad aesthetic inspection.

The source inspection was also too selective. Reading an early `.product-main` declaration suggested a particular maximum width, but a later shared `.cu-workspace` rule has higher specificity and different behavior. The source includes accumulated refinements and token-driven scaling. Copying one early declaration or a few resolved colors is not equivalent to preserving the cascade. The browser's computed result, backed by the relevant winning rules, is the authoritative implementation observation.

The React abstractions introduced additional drift. A generic Columns composition used a fractional split where the source bounded the Contract column. A generic Metadata grid used three columns where the source fitted its fact groups intrinsically. A generic Stack stretched Refresh job but left Start job content-sized. A new full-width summary card inserted an extra level into the detail page. These changes were not detected by badge equality or basic page-bound assertions because they were valid CSS and internally consistent.

There was also a reference-selection error. Some legacy story runtime navigation exposed demo feature labels, while the original US025 product shell and the latest explicit human correction require real product destinations. The recovery plan must resolve that conflict explicitly. It must not select whichever source happens to be easiest to copy. The user has now resolved the required desktop navigation vocabulary; every migrated story must inherit it consistently.

The response is to retain useful engineering checks while adding a separate source-fidelity track. Behavior, implementation ownership, cross-instance consistency and migration fidelity become distinct report sections. None can substitute for the others. The workflow should fail clearly when a fidelity reference is missing, a state is unmatched, or a difference has not been authorized. This is more valuable than adding more prose telling an agent to be careful.

## 3. Authority, source selection and conflict resolution

Use the following authority order for this recovery. First, apply the latest explicit human decisions, including the navigation labels and the rejection of the current migration's layout. Second, use current, specifically accepted component and page behavior from the original implementation. Third, use the selected Round 10 appearance and its documented later refinements. Fourth, use inspected frontend material as supporting context where it does not contradict the first three sources. Existing React code is an implementation candidate, not a source of visual authority.

This ordering matters because the sources do not all describe the same moment. Round 10 contains several subsequent refinements to selection, header surfaces and action trays. The current HTML source contains later minimal-copy, pagination, disclosure and recovery corrections. The frontend shell has its own application implementation and may expose Dashboard or other labels that are not the required design vocabulary. The recovery must not combine unrelated fragments into a new hybrid design and call the result faithful.

Create one compact current reference descriptor. It should identify the selected source root, content hashes of the required runtime files, selected component references, the current scenario map and the applicable human overrides. It should not copy every historical screenshot or retain a sequence of review books. The descriptor is an index into one frozen reference packet. Git and one durable reference archive provide provenance without a second history platform.

For the shared product shell, the explicit current navigation rule resolves the conflict. Use Overview, Services, My Jobs, Invitations and Profile on desktop. Preserve the original compact captions and accessible names where the original intentionally shortens them on mobile. Do not copy the feature-navigation helper in the three-story legacy runtime as the product-shell specification. Record that helper as a source inconsistency superseded by the current human instruction.

For page composition, start from the current original screen for the matching scenario and fixture. For example, original US025 C02 has Job #41 as the page heading, a Surveys context panel, and a Contract panel containing the Accepted badge and agreed price. The React checkpoint instead introduces Job details, an additional summary card, Job overview and Ready to start. Those are observable structural differences. They require correction rather than an exception that retroactively approves the rewrite.

For later usability corrections, preserve the latest meaningful behavior. Do not restore a verbose obsolete paragraph simply because it appears in an older screenshot. Do not reintroduce a Previous control on page one. Do not restore a blocking loading dialog with no escape. Where an older screenshot and the current source differ, identify the current human decision and compare the relevant accepted state. If the conflict cannot be resolved from the available evidence, mark that exact region unresolved and continue independent work elsewhere.

Keep reference status separate from implementation status. A source component can be selected as the migration reference while its palette still awaits human acceptance. A copied component can match the source accurately while remaining aesthetically provisional. A newly proposed improvement can be useful but outside the fidelity pass. These distinctions avoid the previous mistake of treating an agent-reviewed replacement palette or a mechanically consistent composition as accepted design.

The reference descriptor should contain named overrides rather than generic permission to improve anything. Suitable entries identify a component, state, property family, source case, current instruction and expected difference. For example, a modal dismissal recovery requirement can authorize behavior beyond an older capture while preserving its geometry. A desktop navigation override can authorize replacing obsolete demo labels with the explicitly required product labels across all five stories. Nothing should authorize arbitrary card rearrangement.

## 5. What one-to-one fidelity means technically

Treat fidelity as a set of contracts rather than one global similarity score. Semantic fidelity preserves the meaning and grouping of visible information. Geometric fidelity preserves the layout relationships and source sizing rules. Typographic fidelity preserves font files, weights, sizes, line boxes and wrapping. Paint fidelity preserves theme roles, fills, borders, shadows and material behavior. Behavioral fidelity preserves state transitions, focus, dismissal and available actions. Responsive fidelity preserves the transitions among layouts as available space and user settings change.

A screen does not pass because the same words appear somewhere. Moving the Accepted badge from the Contract panel into a new summary panel changes its relationship to the agreed price and task action. Joining two survey titles into a synthetic job heading changes information structure. Removing the count of attached surveys changes visible content. Making Target responses display only a number changes a unit-bearing fact. These are semantic and composition differences even if the interface still looks plausible.

Likewise, matching a single desktop screenshot does not establish responsive fidelity. A fixed 332px button could happen to resemble the original at one width while failing when its panel changes width or the root scale changes. A faithful implementation should reproduce the source relationship: the action fills the bounded Contract panel's content width, subject to its padding and responsive placement. The screenshot measurement verifies the relationship; it should not become a global hardcoded width.

Measurements must identify the box being compared. A main element's border box is not its inner content column. In the exploratory original at 1440px, the outer workspace spans the viewport but has intrinsic horizontal padding. The React main element instead has its own narrower outer width and no equivalent internal padding. Comparing only each element's `x` value would misdescribe the actual content origin. Record outer bounds, padding, content bounds and child anchors separately.

Precision should be strict where the source contract is exact. Navigation labels, active destination, visible fact count, DOM order and action availability are categorical. Font family and selected weight should match their source roles. Root scale should match the source function. Geometry can allow a small documented subpixel tolerance in the canonical environment, but a large difference cannot be hidden behind a percentage threshold or explained away as responsive flexibility.

Do not use pixel equality as the only test. Two images can differ slightly because a material blur interacts with content behind it, while the component's own paint and geometry are correct. Conversely, a small control can be dramatically wrong while the full-page difference ratio is tiny because most of the canvas is blank. Combine whole-page comparison, region comparison, measured anchors and component contracts. Classify each difference instead of forcing one threshold to answer every question.

The word accurate should therefore have a precise reporting meaning. A region is source-matched when it has an equivalent scenario state, matched environment, complete reference, passing semantic and geometric contracts, inspected paired detail, and no unapproved meaningful difference. A page is source-matched only when its relevant regions and composition pass. A story is migration-complete only when its named scenarios and responsive obligations have sufficient coverage. Human palette approval remains a separate field.

## 6. Freeze a compact original reference packet

The reference packet must be runnable without the frontend or backend. It should contain only the current original files needed to render the five migrated stories and shared components, plus required assets and current scenario fixtures. Exclude generated books, old ZIP handoffs, review history, node_modules, unrelated feature drafts and redundant exports. Preserve original Figma/SVG material in its existing read-only location; do not use this recovery as permission to edit or republish those sources.

Inventory the original runtime dependency closure before packaging. Required inputs include the selected theme tokens and recipes, shared component helpers, relevant operation helpers, each story's screen host and composition CSS, fixture definitions, models, fonts, logos and role artwork. Identify browser-local tuning or persisted operation journals that can change the rendered result. A reference that silently loads a stale local draft is not deterministic even if its source files are frozen.

Store a descriptor with relative file paths and content hashes. Include an explicit reference selection date, selected design revision, current human overrides and capture environment. This does not need a database. A small JSON file is sufficient. Derive file lists from the runtime closure and an explicit asset allowlist, then validate that the packet contains no absolute workspace paths or application secrets. The packet is a source reference, not another versioned screenshot book.

Serve the frozen reference read-only through an owned local server during comparison. The server must identify the packet it serves so that the CLI cannot accidentally compare against an older process on the same port. Its identity should include the descriptor checksum, not only a directory path. Check the identity before capture. If the selected port belongs to another process, report the conflict; do not kill an unrelated server or silently attach to it.

Use the same canonical Linux browser environment to capture both original and React. The native Windows audit already produced useful measurements and paired images, but those are exploratory. They must not be compared as pixel goldens against Linux output. Font fallback, rasterization and browser configuration can affect pixels. The official Playwright guidance recommends consistent rendering environments for this reason: [visual comparison documentation](https://playwright.dev/docs/test-snapshots).

Separate the frozen original reference from approved React references. During recovery, the original packet is the migration comparator. After a React region passes parity and receives the required review, its capture can become a React regression reference with explicit provenance. A future React-only regression check answers whether the accepted implementation changed. The original-to-React check answers whether migration fidelity was achieved. Keeping these purposes distinct prevents a new implementation from approving itself.

Use one active original packet and one rollback packet at most. A changed source selection should deliberately replace the descriptor after review. Do not create a packet for every local run. Temporary candidates, paired screenshots, overlays and logs belong in current artifacts with bounded retention. The repository should contain the descriptor and comparison code, while the larger immutable packet and screenshot reference archive can live as private Release assets when ready.

Before any destructive cleanup, prove retrieval from a clean checkout and verify its checksums. Prove that the original can render representative cases without the old workspace. Then prove that all 94 mapped original scenarios remain reachable in the packet. Missing source dependencies must be fixed in the packet selection, not concealed by resolving files from a sibling checkout. The eventual cleanup decision should depend on this proof and human fidelity acceptance, not on the existence of a new repository.

The native audit used matching US025 C02 fixtures, but the page must still be checked for loss of units, invented combined titles, omitted survey rows and changed date presentation.

For operations, prefer controlled adapters and clocks over arbitrary sleeps. A pending source screen should be paired with a pending React screen before either auto-resolves. A successful screen should represent the same confirmed result. An unknown result should expose comparable read/reconciliation actions. If the original persists an operation journal, reset it deliberately for initial-state captures and exercise restoration separately. Examples include a Contract heading and Accepted badge, a saved-proof count, a visible uncertainty banner, or a dialog title with the expected operation state. Wait for that predicate and font readiness before measuring. A screenshot taken before the intended state is stable should be classified as setup failure, not a visual regression. Record the observed predicate in the evidence receipt.

Keep the mapping compact and executable. Extend the existing scenario specifications rather than maintaining a second narrative spreadsheet. Use shared defaults for common environment values and explicit overrides for exceptional states. Validate that every legacy identity has one reachable source setup and one reachable React setup. Duplicate mappings, missing state predicates and unresolved fixture mismatches should fail inventory validation before an expensive screenshot run begins.

## 8. Normalize the product viewport and the workbench frame

The product viewport is the dimensions of the document that renders the product interface. In Storybook it is normally the preview iframe, not the entire browser window. The manager sidebar, toolbar, addon panel and zoom setting change the space available to that iframe. A screenshot of a 2560px browser window does not prove that the product document had a 2560px CSS viewport. The recovery harness must measure the actual product frame.

Record `innerWidth`, `innerHeight`, device scale factor, browser zoom assumptions, document scroll position and the preview element's client dimensions. Also record Storybook's selected viewport and display zoom when reproducing a user report. Treat screenshot display resizing in chat as another separate transformation. A 1280px displayed image can originate from a 2560px browser screenshot; pixel positions in that displayed image are not direct CSS measurements.

Use direct product documents for canonical comparison. Open the frozen original screen and Storybook's `iframe.html` route in separate pages with the same configured viewport. Exclude Storybook manager chrome from product screenshots. Retain a separate manager-context capture only when investigating workbench integration or reproducing a user's annotation context. This makes product geometry comparable without pretending that the source HTML studio and Storybook manager share the same surrounding interface.

For live human review, provide explicit viewport controls and print the current product dimensions in the review receipt. A focused link can open a selected story, theme and material, but the user should not need to infer whether a manager panel is constraining the preview. Where necessary, provide an Open product preview link that bypasses manager chrome. Keep that as a workbench affordance, not a product navigation item.

Use the same viewport orientation and scrollbar policy on both sides. Long content can introduce a vertical scrollbar that changes available inline space in some environments. The reference harness should measure actual layout width after that condition, rather than assuming the configured browser width equals every container's content width. Differences caused by scrollbar presence may reveal a real height or overflow defect and should not be masked automatically.

The canonical environment should pin locale, timezone, fonts, browser revision, platform, device scale and capture options. Exploratory native measurements can help locate a problem quickly, but label them honestly. The current audit covers 390, 1440 and 2560px widths at 900px height in native Windows. Its relative comparisons are useful; it is not the final Linux screenshot matrix and must be reproduced there before acceptance.

Storybook's viewport documentation confirms that viewport controls affect the story iframe: [official viewport guide](https://storybook.js.org/docs/essentials/viewport). The implementation should verify its installed version's behavior with a small acceptance probe. Do not rely on a manager toolbar label alone. A failed dimension assertion should stop capture immediately, because every subsequent geometry or pixel comparison would otherwise be based on the wrong coordinate system.

## 9. Recover the complete cascade before changing values

Inspect the winning CSS and custom-property chain for each measured region. Record stylesheet order, relevant selector specificity, inherited values, component classes, host classes, media conditions and container conditions. Read the complete current source, including late refinement blocks. The goal is a concise explanation of the browser's result, not a new general-purpose CSS cascade engine. Browser computed styles and targeted source inspection are sufficient for this project.

The US025 workspace illustrates the danger of partial inspection. An early page rule sets a narrower `.product-main` width, but the shared recipe `.cu-surface main.cu-workspace` later establishes a 96rem outer cap and intrinsic horizontal padding. The runtime adds the workspace class. Copying the early 70rem declaration into React would still be wrong, even though that declaration exists in the original file. The selected element, class set and winning rule must be verified together.

Extract a dependency explanation for each important value. A desktop Contract width depends on root font size, container width, the detail grid's bounded second column, gap and panel padding. A navigation item depends on chrome typography, target minimum, icon slot, label weight and desktop padding. A button's width may come from its parent's grid alignment rather than the button component's own width. These explanations guide surgical fixes at the correct owner.

Do not flatten inherited values into a long list of hardcoded resolved pixels. Preserve the source expression where it represents real responsive behavior. If the original uses `minmax(18rem, 22rem)` for a column, the React composition should preserve that relationship or a proven equivalent. A measured 374px column at one width is a verification result. It is not permission to replace the expression with 374px everywhere.

Use computed measurements to detect mistakes in the extraction itself. Evaluate the preserved rule at several widths and compare its predicted range with the source browser. If the result differs, inspect a later override, an inherited scale, a box-sizing difference or a different containing block. Do not immediately add a compensating margin. A patch that fixes one width by canceling another wrong value is likely to fail at a nearby breakpoint.

Keep the original and React cascade arrangements simple enough to reason about. The recovery branch may temporarily preserve source class names and grouped CSS while the React markup is ported. That is preferable to simultaneously renaming every selector, redistributing values into new tokens and replacing all compositions. Once parity is demonstrated, refactor one owner at a time while the source comparison remains active. The final architecture can be clean without making cleanup the first migration operation.

The extraction receipt should be current and small. For each owner, retain the source files, winning rule references, semantic role and a few representative computed values. Generated complete style dumps are useful diagnostics but should not become committed documentation. The context command should return the owner and the relevant contract, not thousands of CSS properties. Remove superseded extraction notes once the canonical implementation and tests carry the decision.

## 10. Reproduce viewport scaling and text enlargement

The original scaling system is not the React checkpoint's single 2000px jump to an 18px root. The current original recipe defines viewport scale thresholds at 1440, 1920, 2560 and 3840px, backed by scale tokens. The inspected token values are 1.0625, 1.125, 1.25 and 1.375. With a 16px initial font setting, the corresponding base root sizes are 17, 18, 20 and 22px. Reconfirm these values in the frozen packet before implementation.

Explicit text enlargement multiplies the applicable viewport scale. It must not replace it or accidentally apply it twice. A 200% reading setting on a large display is not equivalent to a normal 16px root with a few larger headings. Track the initial browser font preference, viewport factor and reading factor as separate inputs. Derive the root size from the selected source rules, then let source-relative dimensions respond naturally.

The native audit provides concrete evidence of the current drift. At a 1440px product viewport, original root size measured 17px and React measured 16px. At 2560px, original measured 20px and React measured 18px. Navigation height, brand dimensions, target height, panel width and spacing consequently diverge even where both implementations use rem units. Matching a heading's approximate pixel size cannot repair the rest of that scale chain.

Preserve exceptions for non-text artwork and compact chrome where the source defines them. The original enlarged narrow header keeps certain icons and brand artwork at compact bounds while allowing readable text elsewhere. Do not enlarge the entire logo and every navigation target by the reading factor if the source intentionally avoids that. Conversely, do not cap body text at a fixed pixel size merely to preserve a screenshot. The mapping must identify which dimensions scale and which are independently bounded.

Use scale tests that assert computed relationships rather than copy a single list of coordinates. At each threshold, verify the root factor, body density, chrome font size, heading role and representative target dimensions. At reading settings 150 and 200, verify multiplication, usable wrapping and keyboard access. At widths immediately below and above thresholds, verify the intended transition without unexpected double jumps in layout or navigation mode.

Do not casually convert source rem media queries into pixels using the current computed root. Media-query relative units have defined initial-value semantics; page declarations do not simply redefine their basis. The W3C specification explains this distinction: [Media Queries Level 4, units](https://www.w3.org/TR/mediaqueries-4/#units). Record `matchMedia` results in the test browser and inspect container conditions separately. This prevents circular or incorrect breakpoint calculations when the root itself changes with viewport width.

The recovery must also distinguish browser zoom from the workbench reading control. Browser zoom changes CSS viewport relationships and user-agent behavior; the reading control changes document typography according to the source contract. Test the supported reading controls canonically and include targeted browser-zoom exploration where useful. Do not claim those two tests are interchangeable. The final status should name the setting actually exercised.

## 11. Restore workspace bounds, gutters and page anchors

Start with the outer workspace and work inward. Measure the viewport, workspace border box, workspace padding, inner content box, return link, page heading and first major panel. Repeat at mobile, desktop and large desktop sizes in both themes. These anchors establish whether a later card discrepancy is local or caused by a page-wide origin error. A shared gutter mistake can shift every component while leaving each component internally consistent.

Preserve the source's outer cap and padding relationship. The current original shared workspace caps its outer width at 96rem and uses clamped horizontal padding. At the exploratory 2560px width and 20px root, the outer workspace measured 1920px with a 320px outer margin. Its inner content begins further inside that box. The React checkpoint caps its main at 88rem with an 18px root, producing a 1584px main and a different content origin. Those are different layout systems.

The original outer workspace at 1440px measured the full viewport width, while its internal padding constrained the visible panels. React instead measured a 1392px main starting at 24px. These numbers must not be interpreted as a simple 24px offset correction. Compare inner content edges, not only outer boxes. The correct repair is to recover the source cap, padding and scale rules, then verify that the child anchors land correctly.

Define page anchor contracts in relative terms. The return link's start should align with the intended content edge. The heading should use the source gap below that link. The first content region should use the source heading-to-panel separation. List, detail, recovery and unavailable states should inherit the same applicable page origin. A recovery banner should not cause the page title to jump because the feature renders a different shell wrapper.

Do not center an error or unavailable panel merely because its content is shorter. Inspect the current original correction: some older centered states were explicitly changed to align with the page content. Preserve the final source rule and current human instruction. Test normal, loading, error, access-loss and empty states at the same viewport, comparing their shared anchors while allowing their content heights to differ naturally.

Use logical properties for inline and block relationships where the source already does so. Avoid unnecessary replacement of `inline-size`, `padding-inline` or `margin-block` with physical dimensions during the port. That conversion can hide assumptions about writing direction or change interactions with min/max constraints. The current project is not adding a new locale system, but preserving the source's layout vocabulary reduces accidental differences and keeps future behavior predictable.

A page anchor assertion should report both expected and observed relationships and the likely owning layer. For example, report workspace content-left mismatch separately from Contract internal-padding mismatch. Include source and React measurements at the same key, plus a paired crop. This gives the agent a surgical next step. A generic message saying the screenshot changed by 3% is not enough to distinguish root scale, container width, card padding or content-order defects.

## 12. Restore the product navigation model

Product navigation must preserve the original destinations and vocabulary. The desktop order is Overview, Services, My Jobs, Invitations and Profile. The current explicit user instruction applies across the workbench's product screens, including those whose legacy demo runtime used feature shortcuts. Storybook's sidebar and search already provide feature selection. Duplicating that selection inside the product header changes the interface and makes the migration inaccurate.

Map navigation identity separately from story identity. Sample immediately below, at and above every important transition. Use the engine's actual matched condition to identify the transition point. Add a small width sweep around wrapping boundaries where labels or metadata change line count. Do not exhaustively rasterize every pixel width; use structured measurements to locate discontinuities, then capture representative boundary states. This is cheaper and more informative than multiplying all 94 scenarios by an arbitrary set of device names.

Identify what drives the preferred value: viewport width, parent width, root typography or available content. Confirm the source bounds and behavior at each endpoint. The CSS function's general behavior is documented by [MDN's clamp reference](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/clamp); project-specific expressions still require source measurement.

Short height needs its own contract. A 390px-wide page at 900px height and the same width at 568px can need different chrome or scrolling behavior under enlarged text. Preserve the source's usable reading region and flow fallback. Do not keep a fixed dock and action tray if they consume nearly the entire viewport. Conversely, do not let a short error page pull a supposedly fixed bottom bar into the middle of the screen.

The responsive report should identify each exercised rule and observed transition, not only a list of captured widths. A useful result says that the bounded Contract column becomes stacked under the same source condition and that the primary action moves to the same tray mode. A weak result says that 390px and 1440px screenshots contain no horizontal overflow. Both are useful checks, but only the first establishes the requested responsive mapping.

## 35. Use a focused risk register and diagnostic playbook

Wrong reference selection is the highest risk. A visually coherent React page can be compared against an obsolete or unrelated original case and appear successful. Mitigate this with the authority order, source checksum, explicit state/fixture key and a small source-selection review before capture. If a human correction conflicts with the packet, update the named override or packet deliberately. Do not choose a different original merely because it makes the comparison easier.

Hidden browser state is another high risk. Tuning drafts, operation journals, persisted filters and navigation state can change the original or React without changing the URL. Reset those stores for deterministic initial states, then test restoration as a separate scenario. Record the reset policy. If a capture does not meet its readiness predicate, classify setup failure before image analysis. Do not compensate for hidden state by changing CSS.

Viewport confusion can produce large false discrepancies or hide real ones. Record product iframe dimensions and zoom context, use direct canonical previews, and distinguish outer screenshot coordinates from CSS pixels. If the manager view looks wrong but the direct view matches, investigate manager sizing or workbench configuration. If both differ at matched dimensions, investigate the product implementation. Do not blend those two diagnoses into a vague responsive issue.

Cascade simplification can silently remove a late refinement. When a value differs, inspect winning rules, class sets, custom-property inheritance and active conditions. Verify whether a generic source rule is overridden by a shared workspace recipe or a later manual correction. Restore the intended relationship before adding a patch. A series of negative margins that cancels earlier errors is a warning sign that the ownership diagnosis is wrong.

Overgeneralized React compositions can preserve data while changing meaning. Diagnose extra summary panels, concatenated survey titles, redistributed metadata and stretched actions as composition or view-model defects. Do not try to repair them exclusively in token CSS. The correct owner may be a feature composition or adapter. A global button tweak is unlikely to fix Start and Refresh when their parent columns and width policies differ.

Text and font differences can imitate layout defects. Check actual font loading, root scale, body density, role size, weight and wrapping before changing container dimensions. For multilingual text, inspect the canonical fallback environment. For URLs, distinguish intended segment wrapping from uncontrolled word breaking. If only one theme differs, inspect role mapping and material compositing rather than assuming the same width formula is wrong.

Evidence can also be misleading. A crop may hide a parent shift, fixed chrome may cover a control, and a thumbnail may erase the detail being judged. Use native paired crops, retained context and measured anchors. Record actual inspection limits. Never mark captured-only evidence inspected or enlarge comparison tolerance because the image is difficult to assess. When evidence is insufficient, improve the evidence before changing the interface.

Exercise reference integrity. Test missing packet, wrong checksum, mismatched environment, missing scenario mapping, absent region, stale report and unauthorized promotion. Checking must not regenerate a golden reference. Review must not approve it. A failed publication must retain the old pointer. A clean checkout must retrieve the selected packet and reference with verified checksums. Keep these tests small and focused, using the established tools rather than another orchestration framework.

Exercise responsive boundaries. Introduce a wrong desktop threshold, remove a metadata span or keep fixed chrome under an enlarged short-height condition. Verify that transition and geometry checks fail at the relevant boundary samples. Restore the source behavior and confirm stable neighboring sizes. The test should describe the relationship that broke, not only a changed screenshot number. This makes the failure actionable for a future agent.

Finally, exercise evidence reuse. An unchanged image with the same source/environment identity can inherit actual prior inspection provenance. A changed image must require new review. A source edit after capture must make the report stale. A contact sheet cannot be recorded as individual fine-detail inspection. These are workflow correctness properties, because misleading evidence labels were part of the earlier quality problem. The system should make honest reporting easier than accidental overclaiming.
